Success is not evidence

Four times in three days, something we built reported success while changing nothing. None of them failed loudly. What we now check instead.

November 2026

We were a day from switching on a privacy control across several consumer websites when someone noticed the Publish button had never worked. It looked as if it did. You pressed it, a new version appeared in the history, and the screen said published. But the button was sending a field the API reads as "roll back", so every publish after the first one quietly republished the first one.

Had we flipped the kill switch that week, the console would have reported success and protected nobody.

Four in three days

That would be a good story on its own. It wasn't on its own. In the same three days we found three more places where something reported success and changed nothing:

  • A Roll back button that showed a "rolled back" message and did nothing at all.
  • A rollback job that copied files with a sync command. Sync copies a file only when it is newer or a different size. A rollback copies older files, often of the same size. So the job skipped everything, every time, and reported success every time.
  • A settings dropdown that changed what was on screen, saved nothing, and offered a friendly undo.

None of them failed loudly. We caught them by reading a log, by reading the API's contract, by a deploy step that fetched the live public URL and checked which release it was actually serving, and by a plain survey of the code. In every case the thing that said "done" was describing itself, not the system.

Why AI makes this worse

AI agents write code fast, and they report on their own work just as fast. That means more success messages per day than any team has ever had to read, and each one sounds sure of itself.

One evening a background job took down a service for about seventy seconds. The first account I was given said the job had almost certainly run to completion and written nothing. It was an inference, it was wrong, and it had already travelled as fact. A read-only check of the logs showed the process had been killed for running out of memory. We rebuilt the production image, ran it locally under the same one-gigabyte limit, reproduced the old failure first, and only then measured the fix: the old path peaked above a gigabyte, the new one at 85 megabytes.

An agent's account of its own failure is a claim too. So is mine. The habit that matters is saying "I have not checked" when that is the truth.

Check the thing, not the label

What we changed was less about tools and more about which question each check answers.

Verify what is served, not what was sent. After a deploy, fetch the public URL and read the version in the bytes. A version string is something the build writes next to the code; it is not the code.

Make the bug impossible, not just fixed. The publish defect was fixed by removing the field from that code path entirely, not by correcting one call. A mistake that cannot be expressed cannot come back.

An assertion that equals the default proves nothing. We had three bugs live for weeks because every real value happened to equal the fallback the broken code returned. A correct render and a dead code path looked identical. Tests now drive a deliberately unusual value end to end, so they can actually fail.

Ask whether the gate asks the right question. One contract check confirmed that the API would accept a sample config. The question that mattered was whether that is what the API serves. Because the API quietly upgrades old formats on read, the check stayed green while production moved on without it.

Bytes are not pixels. I once confirmed a styling fix in the shipped file and called it verified. The theme redefined the value underneath it, and the checkbox on screen was still a circle. The lasting fix was a test that renders the real component with the real stylesheet and measures the result, proven by making it fail first.

Distrust a file that exists. A script that saved an error page into a data file looked exactly like one that had worked. Leaving output behind is not the same as producing it.

It cuts both ways

The mirror image is just as costly. Twice in one evening a check told me something was missing right after it had been published correctly: once because the page was cached, once because the code waits ten seconds before reporting and the check waited five. A false "it isn't there" can get a correct change reverted. Before reporting absence, we check twice: a second URL, a cache-buster, and a wait longer than any timer in the path.

What this asks of leaders

Every dashboard, every green build and every closed ticket is a report, and reports describe the reporter. The question that keeps a team honest is short: how do you know? Not "did it succeed", but what did you look at, outside the thing that made the change, that shows it worked for the people it was built for.

That question costs a few minutes per change. The alternative is a kill switch that says it worked.
