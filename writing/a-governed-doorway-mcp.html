A governed doorway: building a shared MCP platform

AI agents need access to enterprise systems. How you grant that access is the whole game — the concept and lessons from building a shared MCP platform.

July 2026

The moment AI agents start doing real work, they need to touch real systems — the ticket tracker, the data warehouse, the deployment pipeline. And the moment that happens, every company faces the same fork in the road, usually without noticing they're at it.

The default path is ad-hoc: each team wires its favorite AI tool directly to each system it needs. It works on day one. By month six you have an N-by-M mess of integrations, credentials scattered across laptops and config files, and no honest answer to the question a board will eventually ask: what can your AI agents touch, and who approved it?

The other path is a platform. That's the one I took, and it's the concept I'd argue every company adopting AI seriously will converge on: one governed doorway through which all agents reach all systems.

The concept

MCP — the Model Context Protocol — has emerged as the standard for giving AI models access to tools. Most companies consume it piecemeal: a vendor server here, a plugin there. The concept I built instead is a shared internal MCP platform: a single service, owned like any other piece of infrastructure, that exposes enterprise systems to AI agents through versioned, provider-based tool contracts.

The design is a hybrid. Standard SaaS tools ride on their vendors' hosted MCP servers — no point rebuilding what already works. Custom and internal workflows go through the shared platform, which owns authentication, authorization, auditing, and observability in one place. Any AI client — different vendors' agents, internal applications — speaks to the same interface and inherits the same governance.

We built it ticketing first: a working provider handling real read and write workflows for project management, with write-paths opt-in and validated against a dedicated test target before touching anything real. Not a slide about future architecture — a running service that agents use every day, with a roadmap of providers behind it.

What building it taught me

Start with one high-value provider, not a framework. The temptation is to design the grand abstraction first. We shipped one provider that solved a real daily workflow, and let the platform shape emerge from the second and third. The abstraction you extract is always better than the one you invent.

Design for many clients from day one. The same tools get called by different AI products and by internal applications. Treating the tool contract as the product — versioned, documented, client-agnostic — is what turns an integration into a platform.

Make writes a privilege, not a default. Read access unlocks most of the value at a fraction of the risk. Our write paths are opt-in per provider, validated against dedicated targets, and auditable. When something goes wrong, you want the blast radius to be a test ticket, not a production database.

Governance is a feature, not friction. The audit trail isn't there to slow agents down — it's what makes it defensible to give them more access over time. Every request through one doorway means adoption and control grow together, instead of trading against each other.

Why executives should care

AI governance debates tend to float at the policy level — principles, committees, acceptable-use documents. Necessary, but a policy can't log a request. The doorway can. If you can't enumerate what your agents can reach, you don't have an AI governance posture; you have a hope. A shared platform turns the hope into architecture — and architecture is something you can inspect, audit, and scale.
